    Use Reducer

    Overview¶

    use_reducer is a ReactPy hook that holds state behind a function: you send an action, and a reducer turns the current state plus that action into the next state. 

    state, dispatch = use_reducer(reducer, initial_value)

    Reach for it when a component's updates are more than "set this to that" — several fields that change together, transitions that depend on what is already there, or update logic you want out of the component so it can be tested as a plain function.

    Reference¶

    use_reducer(reducer, initial_value)¶

    Call use_reducer at the top level of your component.

    from reactpy import use_reducer

    Parameters¶

    • reducer: (state, action) -> new_state. A pure function: given the same two arguments it returns the same result, and it does not touch anything outside them. It must return a new object rather than modifying state — see the reducer must not mutate.
    • initial_value: The state to start with. Pass a function taking no arguments to build it lazily; ReactPy calls it on the first render only. See avoiding recreating the initial state.

    Returns¶

    A two-item tuple, normally unpacked:

    • state: The current state, as of the start of this render.
    • dispatch: A function that takes an action and schedules the update. The same object on every render — verified, one dispatcher across four renders — so it is safe to pass into a child or a dependency list.

    Caveats¶

    • Define the reducer at module level. ReactPy builds the dispatcher once, on the first render, and the dispatcher closes over the reducer you passed then. A reducer defined inside the component is a new function object each render and ReactPy keeps using the first one, so any value it closes over is frozen at its first-render value. Measured: four renders, four distinct reducer objects passed in, and the state kept reporting seen_n=0. This differs from React, which re-reads the reducer every render. Anything the reducer needs must arrive in state or action. See The reducer never changes.
    • use_reducer is use_state underneath. The dispatcher calls the state setter with lambda last_state: reducer(last_state, action), so every rule from use_state applies here — replaced, never merged; equal values schedule no render; mutations vanish silently. See The reducer must not mutate.
    • The reducer runs eagerly, inside dispatch — not later during the render. Verified by ordering statements around the call. A reducer that raises is swallowed the same way any event-handler error is: logged on the server as Failed to execute event handler, with nothing in the browser console.
    • Actions are yours; ReactPy never inspects them. A dict with a "type" key is convention, not a requirement — you can dispatch a string, a number, or a tuple.
    • Like every hook, call it only at the top level — never in a loop, a conditional, or after an early return. ReactPy does not check; a hook that runs on some renders but not others produces a scrambled component and a cryptic IndexError.

    def todos_reducer(state, action):
    """One function per behaviour, chosen by the action's type.

    Defined at module level on purpose: ReactPy builds the dispatcher once, on
    the first render, and keeps that reducer -- a reducer defined inside the
    component would keep its first-render closure forever.

    Every branch returns a NEW dict. Returning the mutated `state` would be
    dropped without a word.
    """
    if action["type"] == "add":
        return {
            **state,
            "items": [*state["items"], {"text": action["text"], "done": False}],
        }
    if action["type"] == "toggle":
        items = [
            {**item, "done": not item["done"]} if i == action["index"] else item
            for i, item in enumerate(state["items"])
        ]
        return {**state, "items": items}
    if action["type"] == "clear_done":
        return {**state, "items": [i for i in state["items"] if not i["done"]]}
    return state


@component
def todo_list():
    state, dispatch = use_reducer(todos_reducer, {"items": []})

    return html.div(
        html.h1(f"To-do ({sum(1 for i in state['items'] if not i['done'])} left)"),
        html.ul(
            [
                html.li(
                    {"key": i},
                    html.button(
                        {
                            "onClick": lambda event, i=i: dispatch(
                                {"type": "toggle", "index": i}
                            )
                        },
                        state["items"][i]["text"],
                    ),
                )
                for i in range(len(state["items"]))
            ]
        ),
        html.button(
            {
                "onClick": lambda event: dispatch(
                    {"type": "add", "text": f"task {len(state['items']) + 1}"}
                )
            },
            "Add task",
        ),
        html.button(
            {"onClick": lambda event: dispatch({"type": "clear_done"})}, "Clear done"
        ),
    )

    The reducer must not mutate¶

    This is the failure mode most likely to cost you an afternoon, and it is silent. A reducer that modifies state and returns it hands back the very object ReactPy already holds; the comparison finds them equal and schedules nothing. No error, no warning, nothing in the console — the button just stops working while your data quietly changes underneath.

    def counter_reducer(state, action):
    # Always return a NEW object. `use_reducer` is built on `use_state`, which
    # compares what you return against what it already holds and schedules no
    # render when the two are equal. Mutating `state` here and returning it
    # would update the data, schedule nothing, and fail with no error and
    # nothing in the browser console.
    return {**state, "count": state["count"] + 1}


@component
def counter():
    state, dispatch = use_reducer(counter_reducer, {"count": 0})
    return html.div(
        html.h1(state["count"]),
        html.button({"onClick": lambda event: dispatch({"type": "inc"})}, "Add 1"),
    )

    loads = []  # demo-only: shows how often the initializer actually runs


def load_config():
    """Stand-in for anything slow: reading a file, querying a database."""
    loads.append(1)
    return {"rows": [{"name": n} for n in ("alpha", "beta", "gamma")], "selected": None}


def reducer(state, action):
    if action["type"] == "select":
        return {**state, "selected": action["name"]}
    return state


@component
def report():
    # Pass a function as the initial state and ReactPy calls it once, on the
    # first render. Passing `load_config()` instead would call it on every
    # render and throw every result but the first away.
    state, dispatch = use_reducer(reducer, load_config)

    return html.div(
        html.h1(f"{len(state['rows'])} rows"),
        html.p(f"selected: {state['selected'] or '-'}"),
        html.p(f"initializer ran {len(loads)} time(s)"),
        html.button(
            {
                "onClick": lambda event: dispatch(
                    {"type": "select", "name": state["rows"][0]["name"]}
                )
            },
            "Select first",
        ),
    )

    use_reducer or use_state?¶

    Prefer use_state. It is shorter and there is no reducer-closure rule to remember. Switch when one of these is true:

    • Several pieces of state always change together, and updating them through separate setters lets the component render in between with an inconsistent mix.
    • The next state depends on the current one in a way you keep writing wrong.
    • The update logic has grown branches you want to name, or unit-test as a plain function.
    • Different parts of a tree need to trigger the same transitions — passing dispatch around is tidier than passing several setters.

    Troubleshooting¶

    My dispatch does nothing¶

    Check the reducer's return value first — this is almost always a mutation. return state after modifying state schedules nothing. Also check for a branch that returns the state unchanged: an action whose "type" no branch matches falls through to your return state, which is correctly a no-op.

    My reducer sees an old value of some state¶

    You defined it inside the component, so ReactPy is running the first-render version with the first-render closure. Move it to module level and pass the value through state or the action.

    The initial value seems to be rebuilt every render¶

    You passed build_initial_state() instead of build_initial_state. ReactPy needs the function itself to know it may skip the work.

    My reducer raised and nothing said so¶

    Expected. Reducer errors land in the server log as Failed to execute event handler and are otherwise swallowed; the state is left unassigned. Look at the server output, not the browser console.

    I want an updater function instead of an action¶

    That is what use_state gives you: set_value(lambda previous: ...). If that is all you need, use_reducer is ceremony you do not owe yourself.

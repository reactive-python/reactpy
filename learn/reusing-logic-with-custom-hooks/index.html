    Reusing Logic with Custom Hooks

    Overview¶

    A custom Hook is a plain Python function whose name starts with use_ and which calls other Hooks. It lets you reuse stateful logic between components — each caller still gets its own state, and nothing about it is special to ReactPy beyond the naming rule that makes the linter work.

    You will learn

    • How to extract a custom Hook, and what it does and does not share
    • Why each call site gets independent state
    • Why passing a callback into a Hook silently freezes it
    • What actually happens when a Hook is called conditionally
    • What reactpy-flake8 can and cannot see inside a custom Hook

    Custom Hooks: sharing logic between components¶

    Consider a shopping list where each row can be selected. The selection logic is stateful, and a second screen will need it too. Pulling it out gives you a function that reads like a Hook and behaves like one:

    def use_cart(items):
    """Selection logic for a list of items — the state lives in the caller."""
    selected, set_selected = use_state([])

    def handler_for(item):
        def toggle(event):
            if item in selected:
                set_selected([name for name in selected if name != item])
            else:
                set_selected([*selected, item])

        return toggle

    return selected, handler_for


@component
def checkout(items):
    selected, handler_for = use_cart(items)
    total = 10 * len(selected)
    return html.div(
        html.ul(
            [
                html.li(
                    {"key": item},
                    html.button(
                        {"onClick": handler_for(item)},
                        f"{item} {'[x]' if item in selected else '[ ]'}",
                    ),
                )
                for item in items
            ]
        ),
        html.p(f"{len(selected)} selected, total ${total}"),
    )


@component
def app():
    return checkout(["apple", "bread", "cheese"])

    Two rules make it a Hook rather than a helper:

    • Its name starts with use_. This is not cosmetic; see below.
    • It is called during rendering, at the top level of a component or another Hook — never in an if, a loop, a callback, or after an early return.

    Hook names must match ^_*use_\w+$¶

    reactpy_flake8 decides what counts as a Hook with a regex, DEFAULT_HOOK_FUNCTION_PATTERN = r"^_*use_\w+$" (reactpy_flake8/run.py). Measured against the same file with only the function name changed, calling it conditionally from a component:

    Function name Reported
    use_form REACTPY102 — hook used inside if
    _use_form REACTPY102
    useForm REACTPY101 — hook used outside component or hook
    get_form REACTPY101

    So the naming rule is what buys you the good diagnostic. A camelCase useForm still gets flagged — but as REACTPY101 at every use_state line inside it, which points at the wrong thing and reads like you called a Hook from the wrong place. Name them use_snake_case, and the linter can tell control-flow violations apart from misplaced calls.

    Not every render-time function needs the prefix

    Add use_ when the function calls Hooks. Leave it off when it does not — a format_rows() or total_price() is an ordinary function, and prefixing it would make the linter police it as a Hook.

    Custom Hooks share logic, not state¶

    A common fear is that a Hook is a singleton. It is not: state is stored per call site, in order. Call the same Hook twice in one component and you get two independent boxes.

    def use_toggle(initial=False):
    on, set_on = use_state(initial)
    return on, (lambda event: set_on(not on))


@component
def panel():
    left, flip_left = use_toggle()
    right, flip_right = use_toggle()
    return html.div(
        html.button({"onClick": flip_left}, f"left {'ON' if left else 'off'}"),
        html.button({"onClick": flip_right}, f"right {'ON' if right else 'off'}"),
        html.p(f"both on: {left and right}"),
    )

    The same Hook called from two different components is equally independent, since each component instance has its own Hook slots. There is no shared registry, no module-level store, and no Context involved.

    This is also why a custom Hook is not a place to put values you want everyone to see. For that, pass props or use create_context (Passing Data Deeply with Context).

    Passing reactive values between Hooks¶

    A Hook receives plain values during render and returns plain values. It re-runs whenever its caller re-renders, so it sees the same props and state the caller does.

    def use_selection(items, limit):
    selected, set_selected = use_state([])
    too_many = len(selected) > limit          # re-evaluated every render
    return selected, set_selected, too_many

    What you cannot do is pass a callback in and list it as a dependency.

@component
def dashboard():
    topic, set_topic = use_state("news")
    last, set_last = use_state("nothing yet")
    tick = use_ref(0)

    def on_result(value):
        tick.current += 1
        # reads `topic` from whichever render created this callback
        set_last(f"{value} #{tick.current} (handler saw topic={topic})")

    use_polling(on_result)

    return html.div(
        html.button({"onClick": lambda e: set_topic(topic + "x")}, f"Topic {topic}"),
        html.p(last),
    )

    def use_polling(topic, on_result):
    latest = use_ref(on_result)
    # always the newest callback, without making it a dependency
    latest.current = on_result

    async def loop():
        while True:
            await asyncio.sleep(0.2)
            latest.current(f"result for {topic}")

    # deliberately excludes on_result: listing it would never help anyway
    use_async_effect(loop, dependencies=[topic])

    def use_profile(show_nickname):
    name, set_name = use_state("name")
    if show_nickname:
        nickname, set_nickname = use_state("nickname")
    else:
        nickname = "-"
    # `bio` is the third hook when the branch is taken and the second when it
    # is not, so it inherits the slot that `nickname` used to own
    bio, set_bio = use_state("bio")
    return name, nickname, bio, set_bio

    What the linter can see¶

    REACTPY102 does fire on the broken file above — hook 'use_state' used inside if statement — provided the function is named as a Hook. That coverage is real and worth wiring into CI. It does not extend to:

    • calling a Hook-conditionally through a wrapper that the linter does not recognise (see the name table above),
    • an early return that skips Hooks declared after it — the pattern people reach for when "toggling off" a feature,
    • a Hook list in one branch matching the caller's expectation in another.

    And it never checks dependency lists, which is the other rule people break. Treat the linter as a partial net and the fix — Hooks at the top level, always — as the actual rule.

    Do not branch to disable a Hook

    # wrong: the second Hook disappears when polling is off
if polling:
    use_async_effect(loop, dependencies=[topic])
    Keep the call and branch inside the Hook body instead, returning None when there is nothing to do. See Lifecycle of Reactive Effects.

    Passing event handlers into custom Hooks¶

    A handler is an ordinary value: pass it in, call it, done — it does not need to be a dependency, and listing it does not make it fresher (measured above). The two shapes that work:

    # the Hook calls it; the ref keeps it current
def use_polling(on_result):
    latest = use_ref(on_result)
    latest.current = on_result
    ...

# or the caller owns the callback entirely and the Hook just hands back a value
selected, toggle = use_cart(items)

    If you find yourself wanting to store a callback so it stays fresh, that is the same problem useEffectEvent solves in React — and ReactPy has no such Hook. The ref-updated-during-render idiom above is the equivalent, with the caveat that reading .current during render makes the render depend on an external value (Manipulating the DOM with Refs).

    When to use custom Hooks¶

    Write one when you have logic — not markup — that two components genuinely need in the same shape. Good candidates in ReactPy:

    • selection, pagination, and form-draft logic
    • a subscription or polling loop with its clean-up wired correctly
    • reading a value from a use_connection-scoped resource
    • a compound updater that several components apply to the same kind of state

    Keep them focused on a concrete use case. A use_async(fetcher, deps) that wraps use_async_effect in generic terms tends to encode one person's cancellation assumptions for everyone; the specific use_polling(topic, on_result) is easier to reason about and easier to change.

    Two things a custom Hook is not:

    • A render bailout. ReactPy has no memo, so extracting a Hook does not reduce how often a component's body runs (Separating Events from Effects).
    • A state container. It cannot share state between components; only props and Context can.

    Recap¶

    • A custom Hook is a function named use_* that calls Hooks; extract one to reuse stateful logic.
    • State is per call site, in call order: the same Hook called twice is two independent boxes (verified).
    • Name them use_snake_case — the linter's regex is ^_*use_\w+$, and camelCase versions get flagged as REACTPY101 instead of the accurate REACTPY102.
    • Never list a callback you were handed as a dependency: it compares code-equal and freezes the Effect on the first render. Read it through a ref updated during render.
    • Conditional Hook calls do not raise; state slots shift and values silently migrate between variables (verified: bio became nickname). Call every Hook unconditionally and branch on the return value.
    • reactpy-flake8 sees control-flow violations inside recognised Hooks, and nothing else — no dependency checks, no wrapper coverage.

    VDOM Mutations

    Overview¶

    A ReactPy element is a dict, and Python lets you assign into it. That is the whole topic of this page: what is safe to change, what is merely pointless, and what quietly corrupts the model that the server is holding on behalf of every connected browser. The rule that decides all of it is that a model is owned by exactly one render — before it, yours to shape; after it, ReactPy's.

    You will learn

    • Why mutation before a render is fine and after it is not
    • Which parts of a built element are copies and which are shared
    • The module-level element that leaks one user's change into everyone's page
    • Safe shapes: build fresh, deepcopy, and transform at build time

    The rule: a model belongs to its render¶

    ReactPy serializes your element to JSON and sends it. Once that has happened, the dictionary is no longer purely yours — the layout keeps live references to the same objects so it can patch a subtree later (core/layout.py, Layout._create_layout_update reuses model.current rather than rebuilding it).

    Split your code on that line:

    • Before the element is returned — mutate freely. Building a model incrementally out of helper functions is normal Python and nothing is watching.
    • After it has been returned from a render — treat it as frozen. Changes now affect a model the client has already received, and the server has no idea they happened.

    Nothing in ReactPy enforces this. There is no freeze, no copy-on-render, no warning. That is why the failure modes below are worth memorizing.

    What is safe before the render¶

    VdomDict is a light dict subclass, and it is strict about its top-level keys — exactly tagName, children, attributes, eventHandlers, inlineJavaScript, importSource:

    d = html.div({"id": "pre"}, "x")

d["tagName"] = "section"       # fine
d["attributes"]["id"] = "a"    # fine — but only because "attributes" exists
d["children"].append("tail")   # fine
d["key"] = 1                   # KeyError: 'Invalid key: key'
d["ref"] = object()            # KeyError: 'Invalid key: ref'

    Note the first line passes an attributes dict. html.div("x") omits the attributes key entirely when there are none — verified, it returns {'children': ['x'], 'tagName': 'div'} — so d["attributes"]["id"] = "a" on such an element raises KeyError: 'attributes' before any guard is reached. Use d.setdefault("attributes", {})["id"] = "a" when the element may not have had one.

    The guard only covers the six top-level names. d["attributes"]["anything"] is unvalidated, and so is every nested value — the validation happens at serialization, and only in debug mode.

    Keys and refs are not top-level keys

    The React shapes {"key": ...} and {"ref": ...} raise, because a VdomDict has no such slot. A key goes inside attributes for an element (html.li({"key": 1}, ...)) or is passed as a keyword to a component (Item(x, key=1)). A ref does not exist at all — see Manipulating the DOM with Refs.

    The same applies to child elements: pass a model you built earlier and the parent stores that object, not a copy. Mutating the child later changes the parent. This is convenient for builders that assemble a tree in stages, and dangerous for anything that outlives the render — which is the subject of the next section.

    Mutating after the render¶

    There are two ways this goes wrong, and they look nothing alike.

    Case 1: the mutation is never sent¶

    Change a rendered element and ask for no re-render, and the browser never learns. This is the same class of bug as mutating state in place, and it shares the cause: ReactPy decides what to send from state changes, not from the shape of your dictionaries.

    There is no error, no log line, and no console message. The element in the browser keeps its old text and you keep staring at the assignment that "obviously" should have worked.

    A mutation you make while handling an event is invisible until something else renders

    This is the version that costs an afternoon. In a real browser, against the shared-element example below: click mutate and the page does not change; click bump, which changes unrelated state, and the mutation appears — as if it had been waiting. Because the re-render walks the model again, it re-reads the dictionary you edited and ships the change with the next patch. A user's action becomes visible on the next action, which is a bug that looks like a timing problem and is not one.

    Case 2: the mutation escapes to other users¶

    The more damaging case, and the one unique to a server-side framework.

    A model built at module level is one object shared by every connection to the server. Each connection gets its own Layout and its own hook state, but they all render the same dictionary. One visitor's handler mutates the object that everyone else's next render reads:

STATUS = html.p({"id": "status"}, "idle")


@component
def panel():
    n, set_n = use_state(0)

    def mark_dirty(event):
        # Mutates the shared element and asks for no render: nothing changes
        # on screen, and the server's model now disagrees with every client.
        STATUS["children"] = [f"mutated by visitor {n}"]

    def bump(event):
        # The next render of ANY state in this component re-sends STATUS --
        # including the mutation, whoever made it.
        set_n(n + 1)

    return html.div(
        html.h1({"id": "counter"}, f"n={n}"),
        html.button({"id": "dirty", "onClick": mark_dirty}, "mutate"),
        html.button({"id": "bump", "onClick": bump}, "bump"),
        STATUS,
    )

    This has no browser-side analogue — in React, module scope is per-tab. Here module scope is per-process, and the process is shared. The rule follows directly: build elements inside the component.     Module-level constants are still fine when they are genuinely inert — a style dict, a list of option labels, an html.head() passed once to ReactPy(html_head=...) — because nothing writes to them. The bug needs a write. If nothing in your program assigns into it, module scope is safe.

    The two mutation habits that also defeat state¶

    These belong to Updating Objects in State and Updating Arrays in State, but they are VDOM mutation seen from the other side, so they are repeated here because the symptom — a control that stops responding with no error — is the one people hunt for longest.

    use_state's setter compares the new value against the old with == (core/hooks.py, strictly_equal). So:

    rows.append(x)
set_rows(rows)          # same object -> compares equal -> no render, no error

    And the corollary that surprises people: a new object that merely compares equal is dropped too, so set_rows([*rows]) when rows is unchanged also renders nothing. Replace state with new, non-equal objects; never edit in place.

    The same comparison is what makes use_memo fail to recompute after a mutate-then-set — the dependency compares equal to itself.

    Safe ways to shape a model¶

    Reach for these in order.

    Build it, do not edit it¶

    The default. Compose with functions, keep elements as return values, and pass data in as arguments. Conditional structure is an expression, not a post-construction edit:

    def row(item):
    return html.li(
        {"key": item["id"], "className": "row" if item["done"] else "row pending"},
        item["text"],
    )

    deepcopy for a genuine fork¶

    When you must derive a variant from a model you do not own — typically something that came back from string_to_reactpy() or a cached template — copy it first:

    from copy import deepcopy

TEMPLATE = html.div({"className": "card"}, html.p("placeholder"))


def card(body_text):
    model = deepcopy(TEMPLATE)
    model["children"][0]["children"] = [body_text]
    return model

    deepcopy preserves the VdomDict class and its key guard, and leaves the original intact — verified. It is the right tool for a template you parse or build once at module level; it is not a licence to mutate a model that has already been rendered.

    Deep-copying a model with handlers duplicates the handler objects

    deepcopy succeeds on a model that has eventHandlers. It builds a new EventHandler but shares the wrapped function, so both copies still invoke the same Python code. That is fine for a fork you intend to render; it is not a way to hand two elements independent handlers — build those separately.

    Transform at parse time¶

    For HTML that arrives as a string, pass *transforms to string_to_reactpy() and edit nodes before anyone has a reference to them — see Convert Between VDOM and HTML.

    Turn the check on while developing¶

    REACTPY_CHECK_VDOM_SPEC validates each rendered model against the JSON schema in core/vdom.py — but only catches structural damage (a child that is not a VDOM dict, a missing tagName), and it is off unless REACTPY_DEBUG is on:

    from reactpy import config

config.REACTPY_DEBUG.current = True   # parents REACTPY_CHECK_VDOM_SPEC on

    It will not catch a className you changed to the wrong string, or a text node you rewrote — those are valid VDOM. Treat it as a schema check, not a mutation detector.

    What you may still touch: the DOM, briefly¶

    Nothing here applies to the browser's DOM, which ReactPy does not share with you. The one sanctioned route is an inline-JavaScript handler, and the same discipline applies there — do not mutate nodes ReactPy owns, since the next patch against a node you removed breaks the diff. That is covered in Manipulating the DOM with Refs.

    Summary¶

    • A model is yours until it is returned from a render; after that the layout holds the same objects.
    • VdomDict guards its six top-level keys — key belongs inside attributes, and there is no ref.
    • Constructors copy the top level but share nested values, so a child element you built is the object the parent holds.
    • Mutating a rendered element sends nothing; the change surfaces on the next unrelated render, which makes it look like a timing bug.
    • A module-level element is shared by every connection, so one user's mutation appears in everyone's page. Build elements inside components.
    • Mutate-then-set-the-same-object is dropped by use_state's equality check, with no error.
    • Prefer building fresh; use deepcopy for a real fork; use parse-time transforms for parsed HTML.

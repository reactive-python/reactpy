    Preserving and Resetting State

    Overview¶

    State is isolated between components. ReactPy keeps track of which state belongs to which component based on their place in the UI tree. You can control when to preserve state and when to reset it between re-renders.

    You will learn

    • How state is tied to a position in the tree
    • When state is preserved, and when it resets
    • How to reset a component's state on purpose, with position or with key
    • Why defining a component inside another one loses state

    State is tied to a position in the tree¶

    When you give a component state, you might think the state "lives" inside the component. It doesn't. ReactPy holds the state, and associates each piece of it with a component by where that component sits in the tree.

    Here counter() is rendered at two different positions:

    Resetting state at the same position¶

    Suppose a scoreboard shows one player's score at a time, and "Next player" swaps Taylor for Sarah:

    counter("Taylor") if is_player_a else counter("Sarah")

    Both branches call counter() at the same position, so ReactPy sees one component whose person prop changed — and the score follows the player over. That's wrong here: Taylor's score and Sarah's score are different things.

    There are two ways to get them treated as separate components.

    Option 1: render them at different positions¶

    Give each player a container that always exists:

    @component
def counter(person):
    score, set_score = use_state(0)

    return html.div(
        {"className": "counter"},
        html.h1(f"{person}'s score: {score}"),
        html.button({"onClick": lambda event: set_score(score + 1)}, "Add one"),
    )


@component
def scoreboard():
    is_player_a, set_is_player_a = use_state(True)

    return html.div(
        # Two containers that always exist, so each player's counter has its
        # own position in the tree. Only one holds a counter at a time, and the
        # container that loses it destroys that state.
        #
        # Do not "simplify" this to *([] if cond else [counter(...)]): an empty
        # expansion contributes no children, so both counters end up at
        # position 0 and ReactPy treats them as one component -- no reset.
        html.div(counter("Taylor") if is_player_a else None),
        html.div(counter("Sarah") if not is_player_a else None),
        html.button(
            {"onClick": lambda event: set_is_player_a(not is_player_a)},
            "Next player!",
        ),
    )

    Each counter is destroyed when its container empties, so every switch starts from zero. This works nicely when there are only a couple of alternatives to lay out side by side.

    An empty list expansion is not a placeholder

    The tempting Python spelling of "or nothing" collapses the whole mechanism:

    *([] if not is_player_a else [counter("Taylor")]),  # wrong: no child at all

    An empty expansion contributes no children, so the two counters land at position 0 and ReactPy treats them as one component — no reset, and Sarah inherits Taylor's score. It is the two html.div() containers above that create the positions. (React avoids this because false still occupies a JSX slot.)

    Option 2: reset state with a key¶

    You have seen "key" when rendering lists. Keys are not only for lists. By default ReactPy identifies a child by its index within its parent — "the first counter", "the second counter" — and a key lets you say this is not the first counter, it is Taylor's counter.

        counter("Taylor", key="Taylor")

    Keys are only unique within their parent

    Two components with the same key under different parents are fine: keys are not globally unique, they only identify a position within one parent.

    Note also that an unkeyed child is identified by its index, which shares a namespace with explicit keys. html.div(contact_list(...), chat(to, key=0)) raises ValueError: Duplicate keys [0], because the unkeyed contact_list() already occupies position 0. Prefix your keys (key=f"chat-{to['id']}") or key all the siblings.

    Keeping state for a component that is no longer rendered¶

    Resetting is often not what you want — a real chat app should restore the draft when you go back to Alice. Keying does not do that: an unmounted component loses its state, so returning to Taylor starts at zero. Options:

    • Render all the chats and hide the inactive ones with CSS. Nothing is unmounted, so state survives. Great for small UIs, wasteful when the hidden trees are large.
    • Lift the state up and keep each recipient's draft in the parent, in a dict keyed by recipient. Children coming and going stops mattering. This is the most common answer.
    • Keep it outside ReactPy entirely — a database, or localStorage in the browser — which you want anyway if a draft should survive a page reload.

    Whichever you choose, a chat with Alice is conceptually different from a chat with Bob, so it still deserves a distinct key.

    Nested component definitions reset state accidentally¶

    This one bites quietly:

    @component
def outer():
    @component
    def nested():
        value, set_value = use_state(...)
        ...

    return html.div(nested())

    Every render of outer() creates a new function object for nested(). A new function is a new component, so ReactPy discards the old state and mounts a fresh one on every render — your state resets itself, with no warning. Measured: a nested child's mount counter climbs by one on each parent render, while a module-level child mounted once.

    Define components at module level, or pass data through props.

    Recap¶

    • ReactPy keeps state for as long as the same component is rendered at the same position.
    • State is not stored in the call that produced the VDOM; it belongs to the tree position you put it in.
    • Force a subtree to reset by rendering it at a different position, or by giving it a different "key".
    • Unkeyed siblings are identified by index, in the same key namespace as explicit keys — prefix your keys to avoid ValueError: Duplicate keys.
    • Don't define a component inside another component, or you'll reset state by accident.

    Responding to Events

    Overview¶

    ReactPy lets you add event handlers to your VDOM. Event handlers are your own functions that will be triggered in response to interactions like clicking, hovering, focusing form inputs, and so on.

    You will learn

    • Different ways to write an event handler
    • How to pass event handling logic from a parent component
    • How events propagate and how to stop them
    • What the event object actually contains

    Adding event handlers¶

    To add an event handler, you first define a function and then pass it as a prop to the appropriate tag. For example, here is a button that doesn't do anything yet:

    1
2
3
    @component
def button():
    return html.button("I don't do anything")

    You can make it show a message when a user clicks by following these three steps:

    1. Declare a function called handle_click inside your def button() component.
    2. Implement the logic inside that function (use print to show the message).
    3. Add "onClick": handle_click to the html.button attributes dictionary.

    You defined the handle_click function and then passed it as a prop to html.button. handle_click is an event handler. Event handler functions:

    • Are usually defined inside your components.
    • Have names that start with handle, followed by the name of the event.

    By convention, it is common to name event handlers as handle followed by the event name. You'll often see "onKeyDown": handle_key_down, "onMouseEnter": handle_mouse_enter, and so on.

    The handler key is camelCase, and it lives in the attributes dict

    This is the single most common mistake when moving from ReactJS examples. The key is the DOM event name in camelCase — "onClick", "onChange", "onSubmit" — and it goes inside the attributes dictionary, not as a keyword argument:

    html.button({"onClick": handle_click}, "Click me")   # correct

    Writing html.button({"on_click": handle_click}, ...) does not raise. ReactPy accepts any on* key as a handler and ships it to the browser verbatim — but no browser event is named on_click, so the button looks fine and simply never fires. Only the names you define (variables, components, component props) are snake_case.

    ReactPy recognises a key as an event handler when it matches ^on[A-Z]\w+ (core/vdom.py, EVENT_ATTRIBUTE_PATTERN).

    Alternatively, you can define an event handler inline with a lambda:

    html.button(
    {"onClick": lambda event: print("You clicked me!")},
    "Click me",
)

    Inline event handlers are convenient for short functions.

    A string is not a handler — it is JavaScript

    ReactPy has a second, easy-to-miss form. If the value of an on* key is a string, ReactPy treats it as JavaScript to run in the browser instead of calling your Python code:

    html.button({"onClick": "alert('You clicked me!')"}, "Click me")

    That renders into an inlineJavaScript field on the VDOM node rather than an eventHandlers field, and nothing on the server ever runs. It is a real escape hatch for things only the browser can do, but it is never what you want when you meant to write a Python function. If your handler silently does nothing, check whether you passed a string.

    Pass the function, don't call it

    Functions passed to event handlers must be passed, not called:

    html.button({"onClick": handle_click}, "...")    # correct: fires on click
html.button({"onClick": handle_click()}, "...")  # wrong: fires during render

    In the second case the () calls handle_click immediately during rendering, without any clicks — because the Python inside the call is evaluated right away, exactly like an expression inside JSX braces. Whatever it returns is then stored as the handler, which is usually None. ReactPy does not reject that: None is serialised as a handler that never runs, so the button renders and does nothing, forever.

    The same trap appears with inline code:

    # This prints when the component renders, not when clicked!
html.button({"onClick": print("You clicked me!")}, "Click me")

# Wrap it in a lambda so it becomes a function to call later.
html.button({"onClick": lambda event: print("You clicked me!")}, "Click me")

    In both working cases, what you pass is a function.

    Passing event handlers as props¶

    Often you'll want the parent component to specify a child's event handler. Consider buttons: depending on where you're using a button() component, you might want to execute a different function—perhaps one plays a movie and another uploads an image.

    Here, toolbar() renders a play_button() and an upload_button():

    • play_button() passes handle_play_click as the on_click prop to the button() inside.
    • upload_button() passes handle_upload_click as the on_click prop.

    Finally, the button() component accepts a prop called on_click and passes it straight to the built-in browser button with {"onClick": on_click}. This tells ReactPy to call the passed function on click.

    Notice the two levels of naming: the prop your own component accepts is an ordinary Python parameter (on_click, snake_case), while the key handed to the browser tag is "onClick". A design system commonly puts styling in components like buttons but leaves the behavior to callers, so play_button() and upload_button() pass handlers down.

    Naming event handler props¶

    Built-in tags like html.button and html.div only support DOM event names as handler keys — "onClick", "onChange", and so on. When you build your own components, however, you can name their handler props anything you like, because they are just Python parameters.

    By convention, name them on_ followed by the interaction:

    In this example {"onClick": on_smash} shows that the browser button still needs the key "onClick", but the prop name received by your own button() component is up to you.

    When a component supports multiple interactions, name handler props after app-specific concepts. A toolbar() could receive on_play_movie and on_upload_image. The calling app() does not need to know what toolbar() will do with them — that's an implementation detail. It could wire them to a click today and a keyboard shortcut tomorrow. Naming props after app-specific interactions gives you that flexibility.

    Use the right tag

    Use the semantically correct HTML tag for the interaction. To handle clicks, use html.button({"onClick": handle_click}) rather than html.div({"onClick": handle_click}). A real browser <button> gives you built-in behavior such as keyboard navigation and focus handling. If you dislike the default styling, restyle it with CSS rather than downgrading it to a <div>. Learn more about writing accessible markup.

    The event object¶

    Handlers receive the event data as their single positional argument. By convention it's called event.

    It is not React's SyntheticEvent. There is no nativeEvent, no persist(), no event pooling. It is JSON that the browser sent over the websocket, wrapped in reactpy.types.Event — a dict subclass that adds attribute access into nested dictionaries:

    def handle_change(event):
    event["target"]["value"]   # dictionary style
    event.target.value         # identical, attribute style

    Both forms are equivalent, and each step down re-wraps the nested dictionary so chaining works. But a missing key reads as None instead of raising, so a typo such as event.target.vallue fails silently. Reach for event.get("target", {}) when a missing value should be a real error.

    The properties that reliably arrive are those the client deliberately keeps:

    Read Meaning
    event["target"]["value"] Text of an <input>, <textarea>, or selected <option>
    event["target"]["checked"] Whether a checkbox or radio is on (use "onChange", which the client maps to input for checkboxes)
    event["target"]["files"] Files from an <input type="file">
    event["key"] Which key, on onKeyDown / onKeyUp
    event["type"] The event name, e.g. "click"
    event["target"]["dataset"] The element's data-* attributes
    event["target"][name] On onSubmit, each named control of the form

    ReactPy's client serializes the DOM event's own enumerable properties, plus the five highlighted ones (value, checked, files, type, name) which it re-reads directly from the element so they survive even when the element hides them, and the current text selection.

    It drops methods, anything __-prefixed or all-caps, and — to avoid enormous payloads and layout thrash — a long denylist of element properties including innerHTML, outerHTML, childNodes, parentNode, offsetWidth, and scrollTop. So event.target.parentNode is simply not there, and neither is anything that would need the real DOM node.

    Form submits hand you the named fields

    For onSubmit the target is the <form> itself, and each control that has a name is flattened onto it. That makes it easy to read a whole form without a use_state per field.

    Event propagation¶

    Event handlers also catch events from any children a component has. We say that an event "bubbles" or "propagates" up the tree: it starts where the event happened, and then goes up.

    ReactPy attaches an ordinary DOM listener to each element, so bubbling is the browser's native behavior rather than something ReactPy implements. That has one consequence worth knowing: unlike React, which delegates every event to the document root and then replays it down your component tree, ReactPy's handlers follow the real DOM tree. A parent handler fires for events from anything nested inside it, including elements you did not render yourself.

    This <div> contains a button. Both the <div> and the button have their own "onClick" handlers. Which do you think fire when you click the button?

    Scroll does not bubble

    Because propagation is the browser's own, the browser's exceptions apply. "onScroll" does not bubble: attaching it to an ancestor will not catch scrolls from descendants. Attach it to the element that actually scrolls.

    @component
def button(on_click, *children):
    def handle_click(event):
        # Detected from this line, so the client stops the event before
        # it reaches the parent's handler.
        event.stopPropagation()
        on_click()

    return html.button({"onClick": handle_click}, *children)

def toolbar():
    messages, set_messages = use_state([])

    def handle_toolbar_click(event):
        set_messages([*messages, "You clicked on the toolbar!"])

    def handle_play_click():
        set_messages([*messages, "Playing!"])

    return html.div(

    ReactPy detects this call by reading your bytecode

    event.stopPropagation() is a no-op on the server — by the time your handler runs, the browser event is long gone. What actually stops propagation is a flag sent to the browser in advance, and ReactPy derives it by inspecting the bytecode of your handler (core/_event_inspect.py, inspect_event_handler).

    It looks for .stopPropagation (and .preventDefault) accessed directly on the first parameter. That produces some sharp edges, all of them observable:

    • The handler must take a parameter at all. def handler(): can never be detected.
    • It must be the first positional parameter. Renaming it is fine; the position is what matters.
    • Rebinding defeats it. e = event followed by e.stopPropagation() is not detected, and propagation silently continues.
    • Passing the event into a helper that calls it is likewise not detected.

    When in doubt, skip detection and declare the intent explicitly:

    from reactpy import event

@event(stop_propagation=True, prevent_default=True)
async def handle_click(event): ...

    Call event.preventDefault() the same way to stop the browser's built-in action. The classic case is a form submit, which would otherwise navigate away from the page:

    @component
def signup():
    signed_up, set_signed_up = use_state(0)
    name, set_name = use_state("")

    def handle_name_change(event):
        set_name(event["target"]["value"])

    def handle_submit(event):
        # Without this line the browser would navigate away from the page.
        event.preventDefault()
        set_signed_up(signed_up + 1)
        set_name("")

    return html.form(
        {"onSubmit": handle_submit},
        html.input({"value": name, "onChange": handle_name_change}),
        html.button({"type": "submit"}, "Sign up"),
        html.p(f"{signed_up} signed up"),
    )

    Capture-phase handlers

    To see an event on the way down, before your children handle it, append Capture to the event name:

    html.div(
    {"onClickCapture": handle_toolbar_click},
    html.button({"onClick": handle_play_click}, "Play Movie"),
)

    ReactPy forwards the key untouched, and the client registers it with addEventListener("click", handler, True), so "onClickCapture" fires before the button's own "onClick". This works because it maps onto a real DOM capability rather than a React invention — which also means the ordering is the browser's, not ReactPy's.

    Can event handlers have side effects?¶

    Yes. Unlike component bodies, which must stay pure, event handlers run in response to an action rather than during rendering, so they are the correct place to change things. See Where you can cause side effects for where side effects belong and why.

    Recap¶

    • Add a handler by putting the DOM event name in camelCase into the attributes dictionary: {"onClick": handle_click}.
    • Only names you define are snake_case; "on_click" renders but never fires.
    • Pass a function, never the result of calling one; a string value means client-side JavaScript, not Python.
    • Handlers may read props, call setters, and have side effects.
    • The event object is a dict-subclass snapshot of browser data, not a SyntheticEvent; read event["target"]["value"], event["key"], and friends, and don't expect DOM-node properties.
    • Events bubble natively, with the browser's own exceptions such as "onScroll". Stop them with event.stopPropagation(), which is detected from your bytecode — or declare it with @event(stop_propagation=True).

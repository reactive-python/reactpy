    You Might Not Need an Effect

    Overview¶

    Most Effects are unnecessary. If your logic only adjusts one thing based on another thing you already have, it belongs in the render — not in an Effect. This page walks through the common cases where an Effect looks right and isn't, with the render counts each one costs.

    You will learn

    • How to recognize an Effect that is doing a render's job
    • What to write instead, case by case
    • Why ReactPy cannot use React's "set state during render" escape hatch
    • Which Effects genuinely are necessary

    How to remove unnecessary Effects¶

    Work through each Effect in your code and ask: does this code need to run after a render, or could it run while rendering?

    An Effect is genuinely necessary when the component must reach something outside ReactPy — subscribing to a queue, opening a socket, starting a task. Everything below is the opposite case: the "external system" is a value your component already has.

    If you're not sure what Effects are for in the first place, start with Synchronizing with Effects.

    When something can be calculated from existing props or state, don't put it in state. Calculate it during render. Fewer state variables means less code, no way for two of them to drift apart, and half the renders. If this feels unfamiliar, Thinking in React covers what belongs in state.

    How expensive is too expensive?

    If you're not sure whether a calculation is costly enough to worry about, write it without caching first, then measure it: time the component body, or count how often it runs. In practice the work that is genuinely slow is usually obvious — parsing, sorting or filtering thousands of rows, regex over a large string, cryptographic hashes. String concatenation, len(), and a loop over a page's worth of items are not worth a cache, and a cache costs more than it saves when its dependency list is wrong.

The value is recomputed exactly when the inputs it reads change, and never on a render that didn't change them.

    Two properties worth knowing, both verified:

    • use_memo infers its dependencies the same way use_effect does — from the names the function reads. Pass dependencies=[] to pin a value forever, or dependencies=None to recompute on every render. See Use Memo.
    • It caches the value, not the render. The component body still runs on every render; ReactPy has no component-level memo, so a child re-runs whenever its parent does. use_memo saves the computation, never the render — see Render and Commit.

    Mutating a value in place and "setting" it back defeats use_memo too, for the same reason it defeats use_state: the new value compares equal to the old one. Build a new object instead (Updating Arrays in State).

    Passing key=user_id tells ReactPy that a different user_id means a different component instance. It tears down profile() and everything below it and builds them again, so all of their state starts fresh. One line, and it covers every piece of state in the whole subtree — no Effect, and no remembering to add one to each nested component.

    The Effect version (set_comment("") in an Effect depending on user_id) is worse in three ways: the subtree renders once with the previous user's draft still in it, every nested component needs its own copy, and a piece of state added later silently fails to reset. See Preserving and Resetting State for the full mechanism.

    key is spelled differently for elements and components

    Here it is a keyword argument to the component call: profile(user_id, key=user_id). On an element it goes in the attribute dict instead: html.li({"key": 1}, ...). Put it in the wrong place and you get TypeError: Vdom.__call__() got an unexpected keyword argument 'key', or a literal key="..." attribute in the page.

    Adjusting some state when a prop changes¶

    Sometimes you don't want to throw state away — just invalidate part of it when an input changes. A list keeps a selection, and a new items prop should clear it. React's advice is to call the setter during render, and that escape hatch does not work in ReactPy. Measured, the render-phase-setter version takes four renders and the client receives this sequence:

    <root>                     items: [a,b,c]     selected: None
/children/0/children/1     items: [a,b,c]     selected: a
<root>                     items: [a,b,c,i4]  selected: a     <-- stale, and delivered
/children/0/children/1     items: [a,b,c,i4]  selected: None

    React throws the discarded render away; ReactPy hands the model to the socket as soon as it exists, so the stale frame ships. Use a derived read instead. Store the value alongside what it belonged to, and let the read decide whether it is still valid:

    @component
def list_box(items):
    is_reverse, set_is_reverse = use_state(False)
    # One state value that remembers which list the choice belonged to. The
    # selection is *derived*: if the items changed, the old choice is not
    # valid for the new list, so it reads back as None. No Effect, no
    # intermediate render with a stale selection.
    chosen, set_chosen = use_state({"items": None, "value": None})
    selection = chosen["value"] if chosen["items"] == items else None

    shown = items[::-1] if is_reverse else items

    return html.div(
        html.p(f"items: {shown}  selected: {selection}"),
        html.button(
            {"onClick": lambda event: set_is_reverse(not is_reverse)}, "Reverse"
        ),
        html.button(
            {"onClick": lambda event: set_chosen({"items": items, "value": shown[0]})},
            "Select",
        ),
    )


@component
def app():

    return html.div(

    The general shape is a guard on the read rather than a call to the setter:

    Do not set state from an Effect that depends on it

    The reflexive alternative — an Effect calling set_selection(None) with dependencies=[items] — is not merely slow. When the value it sets is one it also reads, it is a loop, and ReactPy has no detector for one. Measured: an Effect that set a counter it depended on rendered 86 times before the probe gave up. If a component visibly spins, read what the Effect awaits, what it depends on, and what it sets.

    What you must not do is call the parent's function from an Effect that watches a value.     Chains of computations¶

    When several values feed each other, keep the whole chain in render. Each intermediate is a local variable, not a state variable:

    @component
def report(rows, currency):
    priced = [(*row, row[1] * RATES[currency]) for row in rows]
    total = sum(item[-1] for item in priced)
    heading = f"{currency.upper()}: {total:,.2f}"
    return html.div(html.h1(heading))

    An Effect at any link in that chain means every upstream change costs an extra full render — and, as above, each of those renders is visible to the client. If one link is genuinely expensive, wrap that one in use_memo rather than putting the whole chain in state.

    Initializing the application¶

    Code that should run once per process does not belong in a component at all — a component's Effect runs once per connection, and a server serves many connections:

    # module level, or the ASGI app's startup: runs once
configure_logging()
POOL = create_pool()

    Keep a dependencies=[] Effect for work that is genuinely per-connection, such as a subscription or a session-scoped task. Never guard a process-level side effect with my_component.started = True: the function object is module-scope, so the first visitor flips the flag for everyone (VDOM Mutations).

    @component
def clock_view():
    # The value is owned by `clock`, not by this component, so it cannot be
    # derived during render -- ReactPy has to be told when it changes.
    ticks, set_ticks = use_state(clock.get())

    def effect():
        # Subscribe, and hand back the unsubscribe. This is what an Effect
        # is for: the source of truth lives outside ReactPy.
        def on_change():
            set_ticks(clock.get())

        return clock.subscribe(on_change)

    use_effect(effect, dependencies=[])

    return html.div(html.h1(f"{ticks} ticks"))

    @component
def report_view(name):
    # Store the response *with the name it belongs to*, so a render for a new
    # report cannot display the old one's rows. The empty read is the
    # "loading" state -- derived, not a second state variable.
    loaded, set_loaded = use_state({"name": None, "data": {}})

    async def load():
        data = await catalog.fetch(name)
        set_loaded({"name": name, "data": data})

    use_async_effect(load, dependencies=[name])

    raw = loaded["data"] if loaded["name"] == name else {}

    if not raw:
        return html.p("loading...")

    # Right: the shape the page needs is computed here, from the data that
    # arrived. There is no second state variable to keep in step, so there is
    # nothing for an Effect to synchronise.
    rows = [{"label": key.title(), "value": value} for key, value in raw.items()]
    total = sum(row["value"] for row in rows)
    lines = [
        html.li({"key": row["label"]}, f"{row['label']}: {row['value']}")
        for row in rows
    ]

    return html.div(
        html.h2(f"{name}: {total} total"),
        html.ul(lines),
    )

    The example carries one more lesson in its state shape. It stores the response together with the name that produced it and derives the read:

    raw = loaded["data"] if loaded["name"] == name else {}

    Storing the response alone looks fine and is wrong: switch from orders to users and the component re-renders immediately, before the new response arrives, so the client receives users: 55 total above the orders rows — 55 being orders' total. Measured, and the derived read above is what fixes it, without remounting the component.

    The anti-pattern is a second Effect that watches the response and sets three more state variables from it. Each of those is a value you can calculate, and each adds a render in which the page is half-updated.

    Because ReactPy already runs on the server, there is usually a better option than fetching in the child at all: fetch in a parent during render, or at startup, and pass the result down as a prop. Then the child has no Effect and no loading state, and the response is shared rather than re-requested. Keep the Effect for data that depends on something only the connection knows, like use_location.

    How to tell whether an Effect is necessary¶

    The Effect... Verdict
    reads state or props and sets other state unnecessary — compute it during render
    caches a calculation unnecessary — use_memo
    resets state when a prop changes unnecessary — pass a key
    invalidates state when a prop changes unnecessary — derive the read from what it belonged to
    runs logic shared by two handlers unnecessary — call a function
    reacts to a user action unnecessary — put it in the event handler
    calls a parent's callback when a value changes unnecessary — call it from the handler
    subscribes to a queue, socket, or store necessary, with a clean-up
    starts async work that outlives the render necessary, with use_async_effect
    starts per-connection work on mount necessary, with dependencies=[]

    If you cannot name what the Effect is synchronizing with, it is probably doing a render's job.

    Two failure modes that cost hours

    • An Effect that sets state it depends on loops silently. ReactPy has no loop detector. Measured: 86 renders and counting before the probe stopped.
    • Hooks do not work inside an effect body. use_context, use_state, and friends all raise RuntimeError: No life cycle hook is active. Are you rendering in a layout? — effects run in their own task, with no hook on the stack. Read what you need during render and let the closure carry it in. The traceback appears only in the server log; the page just goes quiet.

    Recap¶

    • An Effect runs after a render. If the work could happen during the render, it should.
    • Values calculated from props or state are not state. Compute them; do not store and re-sync them. Measured: the Effect version costs twice the renders and ships a wrong first frame.
    • use_memo caches expensive calculations without adding a render — but it caches values, not component renders.
    • Reset state with a key, not with an Effect.
    • ReactPy cannot use React's render-phase setter trick: the stale patch reaches the client. Derive the value instead.
    • Sharing logic between handlers, notifying a parent, and submitting a form are all handler work.
    • Subscriptions and async streams are the real use for Effects — with a clean-up, always.

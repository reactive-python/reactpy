    Tutorial: Tic-Tac-Toe

    Overview¶

    You will build a small tic-tac-toe game. This tutorial assumes no prior ReactPy knowledge, and the techniques it covers — components, props, state, and lifting state up — are the ones you will use in every app you write.

    Note

    This tutorial is for people who prefer to learn by doing. If you would rather meet each concept one at a time, start with Your First Component instead.

    The tutorial is divided into four sections:

    • Setup for the tutorial gives you a starting point.
    • The basics teaches you the fundamentals: components, props, and state.
    • Completing the game teaches you the most common techniques.
    • Adding time travel shows why immutability matters.

    from reactpy import component, html, use_state


@component
def square(value, on_click):
    return html.button(
        {"className": "square", "onClick": on_click},
        value,
    )


@component
def board(x_is_next, squares, on_play):
    def handle_click(i):
        def inner(event):
            """
            Due to a quirk of Python, if your event handler needs args other than
            `event`, you will need to create a wrapper function as seen above.
            Ref: https://pylint.readthedocs.io/en/stable/user_guide/messages/warning/cell-var-from-loop.html
            """
            if calculate_winner(squares) or squares[i]:
                return

            next_squares = squares.copy()
            next_squares[i] = "X" if x_is_next else "O"
            on_play(next_squares)

        return inner

    winner = calculate_winner(squares)
    status = (
        f"Winner: {winner}" if winner else "Next player: " + ("X" if x_is_next else "O")
    )

    return html.fragment(
        html.div({"className": "status"}, status),
        html.div(
            {"className": "board-row"},
            square(squares[0], handle_click(0)),
            square(squares[1], handle_click(1)),
            square(squares[2], handle_click(2)),
        ),
        html.div(
            {"className": "board-row"},
            square(squares[3], handle_click(3)),
            square(squares[4], handle_click(4)),
            square(squares[5], handle_click(5)),
        ),
        html.div(
            {"className": "board-row"},
            square(squares[6], handle_click(6)),
            square(squares[7], handle_click(7)),
            square(squares[8], handle_click(8)),
        ),
    )


@component
def game():
    history, set_history = use_state([[None] * 9])
    current_move, set_current_move = use_state(0)
    x_is_next = current_move % 2 == 0
    current_squares = history[current_move]

    def handle_play(next_squares):
        next_history = history[: current_move + 1]
        next_history.append(next_squares)
        set_history(next_history)
        set_current_move(len(next_history) - 1)

    def jump_to(next_move):
        return lambda _event: set_current_move(next_move)

    moves = []
    for move, _squares in enumerate(history):
        description = f"Go to move #{move}" if move > 0 else "Go to game start"

        moves.append(
            html.li(
                {"key": move},
                html.button({"onClick": jump_to(move)}, description),
            )
        )

    return html.div(
        {"className": "game"},
        html.div(
            {"className": "game-board"},
            board(x_is_next, current_squares, handle_play),
        ),
        html.div({"className": "game-info"}, html.ol(moves)),
    )


def calculate_winner(squares):
    lines = [
        [0, 1, 2],
        [3, 4, 5],
        [6, 7, 8],
        [0, 3, 6],
        [1, 4, 7],
        [2, 5, 8],
        [0, 4, 8],
        [2, 4, 6],
    ]
    for line in lines:
        a, b, c = line
        if not squares:
            continue
        if squares[a] and squares[a] == squares[b] and squares[a] == squares[c]:
            return squares[a]

    return None

    The basics: components, props, and state¶

    Inspecting the starter code¶

    The example defines a component. In ReactPy, a component is a function that returns what part of the interface should look like. Read it line by line:

    @component
def square():
    return html.button({"className": "square"}, "X")

    The first two lines are boilerplate: @component turns the function below it into a component, and html gives you a function for every HTML tag.

    The def square(): line defines a function called square. Unlike React, ReactPy component names are snake_case and lowercase — there is no capital-letter rule, because ReactPy tells a component from an HTML tag by whether you call it, not by how it is spelled.

    The return line gives back a button. html.button(...) is a call to a function, not an element literal: children come after the attribute dictionary as positional arguments, so "X" is the text inside the button. {"className": "square"} is that attribute dictionary, and className is the DOM attribute name — attribute keys are forwarded to the browser verbatim, so they keep React's camelCase spelling.

    Building the board¶

    The board needs nine squares, not one. Copying the button twice is tempting:

    @component
def square():
    return html.button({"className": "square"}, "X"), html.button({"className": "square"}, "X")

    That does not fail the way React's "adjacent JSX elements" error does. The comma builds a two-item tuple; ReactPy does not know you meant two children, coerces it with str(), and the page shows the VDOM dictionaries as literal text:

    1
    ({'children': ['X'], 'attributes': {'className': 'square'}, 'tagName': 'button'}, ...)

    Verified through Layout.render(): the model's only child is that string. If the page ever shows you a Python repr, a missing call or a stray comma is the usual cause. A component returns exactly one thing. To return several children, wrap them in a fragment with html.fragment(...), which groups children without adding an element of its own:

    @component
def square():
    return html.fragment(
        html.button({"className": "square"}, "X"),
        html.button({"className": "square"}, "X"),
    )

    # TODO

    Notice how board and square are both called the same way, with no ceremony, while html.div and html.button are calls into the html object. Components are just functions you wrote; tags are functions ReactPy provides.

    Props are read-only. square cannot assign to value to change what its parent passed, and ReactPy has no mechanism to help it try. Data flows down; to change it, the component that owns it must change it.

    Making an interactive component¶

    Now make a square fill itself when clicked. Add a handler inside square and register it under onClick:

    @component
def square():
    def handle_click(event):
        print("clicked!")

    return html.button({"className": "square", "onClick": handle_click})

    A handler is any callable, and ReactPy calls it with exactly one argument — the event payload. Name it event, even if you ignore it.

    Unlike React, there is no browser console to open: ReactPy components run on the server, so print lands in the terminal running your app, next to the URL. Click a square several times and you will see the line repeat there.

    Pitfall

    The key must be camelCase onClick. The React-looking on_click is accepted and shipped to the browser like any other on* key — and then nothing listens for it, because no browser event is named on_click. Verified: the server-side model holds a registered on_click handler while clicking the button leaves the component's state at 0. The button renders, looks normal, and never fires, with no error and no log line anywhere. If a control does nothing, check the spelling of the key first. See Responding to Events.

    value, set_value = use_state(EMPTY_SQUARE) unpacks a pair: the state you read and the setter you call. Its argument is the starting value, used only on the component's first render. Calling set_value asks ReactPy to render the component again, and that render sees the new value.

    The value is None, meaning "empty", and ReactPy renders None as nothing, so a fresh board is blank. It lives in a module-level constant annotated str | None, which is what lets a type checker accept both None and "X" in that square — without it, the type is inferred from None alone and assigning a mark is flagged. See Use State.

    Note that ReactPy renders True and False as the words True and False, so None is the only value that disappears — React's habit of writing cond && <X/> has no working Python equivalent. See Conditional Rendering.

    Click each square and watch them fill independently. Nine square() calls contain nine separate use_state calls, and each one keeps its own value.

    That is a defect, not a feature. Each square's value lives inside that square, so no other part of the program can see the whole board — which means nothing can answer "has someone won?". The next section fixes this by moving the state to where the whole board is visible.

The cause is that set_squares(squares) passes back the very same object that is already in state. ReactPy compares the new value against the current one, finds them equal, and skips the render — an optimisation that turns an in-place mutation into a silent no-op.

    Pitfall

    Mutate-then-set-the-same-object is the most common ReactPy bug and the quietest one. squares[i] = "X" followed by set_squares(squares) schedules no render at all. Neither does mutating without calling the setter. Always build a new list — squares.copy(), a list comprehension, or slicing — and pass that. See Updating Arrays in State.

    Immutability earns its keep twice here. It is what makes the board update at all, and it is what lets the last section keep every past move around: because old lists are never modified, they stay valid and can be re-displayed later.

    Deep Dive

    React's version of this section argues that immutability lets React skip re-rendering parts of the tree that did not change. That argument does not apply to ReactPy: there is no memo and no render bailout, so a child component's body re-runs whenever its parent renders, even with identical props. Immutable data is still required — for the reason above, and so equality checks mean what you expect — but do not expect it to save you renders. See You Might Not Need an Effect.

    Pitfall

    With REACTPY_DEBUG on, the server logs Key not specified for child in list ... for every row. ReactPy is telling you the same thing React does: a list you will re-render needs a key on each item. It is a warning, not an error, so a list can ship without one — and misbehave later in ways that are hard to trace back. The fix is Picking a key.

    A related trap: pass a list, not a generator. html.ol(html.li(...) for ... in ...) skips the key check entirely, with the warning Did not verify key-path integrity of children in generator ... - pass a sequence, and an iterator stored in state is worse still — it is single-use, so the first render shows the rows and every later render shows nothing.

    Picking a key¶

    When you re-render a list, ReactPy has to work out which item is which. It cannot read your intent, so you tell it: give each item a key.

    html.li({"key": move}, html.button({"onClick": jump_to(move)}, description))

    key is a reserved name, and it is spelled two different ways depending on what you are creating — mixing them up is a hard error:

    You are creating Spell it Passing it the other way raises
    an element inside the attribute dict: html.li({"key": move}, ...) TypeError: Vdom.__call__() got an unexpected keyword argument 'key'
    a component as a keyword: row(item, key=item["id"]) silently meaningless, since the dict is the attribute dict

    A key identifies an item across renders. Change a component's key and ReactPy destroys it and builds a fresh one, discarding its state — which is a useful trick on its own, and the subject of Preserving and Resetting State. Keys need only be unique among siblings, not globally.

    For the move list, the move's index is a legitimate key: moves are never reordered, inserted in the middle, or deleted, so index and identity agree. That is the exception. When items can be added or removed, the array index stops identifying anything, and state quietly lands on the wrong row — use a real identifier instead. See Rendering Lists.

    Implementing time travel¶

    jump_to(move) only has to say which move you are looking at:

    def jump_to(move):
    def inner(event):
        set_current_move(move)

    return inner

    And the values derived during render must follow current_move rather than the end of the list:

    x_is_next = current_move % 2 == 0
current_squares = history[current_move]

    Playing a move now has one more rule. If you jump back and play from there, the moves after that point are no longer the future — they are discarded:

    def handle_play(next_squares):
    next_history = history[: current_move + 1]

def game():
    history, set_history = use_state([[None] * 9])
    current_move, set_current_move = use_state(0)
    x_is_next = current_move % 2 == 0
    current_squares = history[current_move]

    def handle_play(next_squares):
        next_history = history[: current_move + 1]
        next_history.append(next_squares)
        set_history(next_history)
        set_current_move(len(next_history) - 1)

        return lambda _event: set_current_move(next_move)

        {"className": "game"},
        html.div(
            {"className": "game-board"},
            board(x_is_next, current_squares, handle_play),
        ),
        html.div({"className": "game-info"}, html.ol(moves)),

    Pitfall

    Do not store one board and a separate list of moves that points into it. The history must own the boards, and the boards must never change once stored. If you find yourself reaching for deepcopy here, that is a sign something is still being mutated — with the code above, the boards are never modified after they are created, so a plain slice is enough.

    Final cleanup¶

    The finished game holds its state in three places, each as low as it can be while still seeing what it needs:

    • game owns history and current_move, because it renders both the board and the move list.
    • board owns nothing. It receives x_is_next, squares, and on_play.
    • square owns nothing. It receives value and on_click.

    That is the pattern this tutorial was built around. State belongs to the component that needs it and to every component above it — no lower, because then a sibling cannot see it, and no higher, because then unrelated renders redo the work. When two components need the same data, lift it to their nearest common ancestor.

    Wrapping up¶

    • A component is a @component function returning one thing; several children go inside html.fragment(...) or a list.
    • Props are ordinary Python parameters, and they are read-only.
    • use_state gives a component memory; calling the setter re-renders it.
    • Handlers take exactly one argument, the event. Extra context is bound on the Python side, usually with a factory function.
    • Never mutate a list you have put in state — copy it, or the setter silently does nothing.
    • Derive what you can during render instead of storing it: winner, x_is_next, current_squares.
    • Lift state to the lowest component that can see everything that needs it.
    • Give list items a key — in the attribute dict for elements, as a keyword for components.
    • Time travel is free once your data is immutable, and impossible when it is not.

    State: A Component's Memory

    Overview¶

    Components often need to change what's on the screen as a result of an interaction. Typing into a form should update the input field, clicking "next" on an image carousel should change which image is displayed, clicking "buy" should put a product in the shopping cart. Components need to "remember" things: the current input value, the current image, the shopping cart. In ReactPy, this kind of component-specific memory is called state.

    You will learn

    • How to add a state variable with use_state
    • What pair of values use_state returns
    • How to add more than one state variable
    • Why state is called local

    The handle_next event handler is updating a local variable, index. But two things prevent that change from being visible:

    1. Local variables don't persist between renders. When ReactPy renders this component a second time, it renders it from scratch — it doesn't consider any changes to the local variables.
    2. Changes to local variables won't trigger renders. ReactPy doesn't realize it needs to render the component again with the new data.

    Both were checked against this exact component: clicking "Next" three times leaves the served VDOM byte-identical, and a later render caused by real state shows index back at 0 even though the handler had bumped it to 3.

    To update a component with new data, two things need to happen:

    1. Retain the data between renders.
    2. Trigger ReactPy to render the component with new data (re-rendering).

    use_state provides those two things:

    1. A state variable to retain the data between renders.
    2. A state setter function to update the variable and trigger ReactPy to render the component again.

    Adding a state variable¶

    To add a state variable, import use_state from reactpy at the top of the file:

    from reactpy import component, html, use_state

    Then replace this line:

    index = 0

    with

    index, set_index = use_state(0)

    index is a state variable and set_index is the setter function.

    Python gives you the destructuring for free

    React's const [index, setIndex] = useState(0) needs array destructuring syntax. In Python this is ordinary tuple unpacking, so there is nothing new to learn here — and unlike JavaScript, leaving out a name is a syntax error rather than a silent undefined.

    This is how they work together in handle_next:

    def handle_next(event):
    set_index(index + 1)

    The handler needs nonlocal to read its own variable

    If you keep the plain-variable version, the assignment inside the nested function is not legal Python without a declaration:

    def handle_next(event):
    nonlocal index
    index = index + 1

    Without it, Python treats index as a new local of handle_next, and reading it on the right-hand side raises UnboundLocalError. This is a Python scoping rule, not a ReactPy one — JavaScript closures just work. With use_state you never need it, because you read index and call set_index instead of assigning.

    Meet your first Hook¶

    In ReactPy, use_state, as well as any other function starting with use, is called a Hook.

    Hooks are special functions that are only available while ReactPy is rendering (which we'll get into in more detail on the next page). They let you "hook into" different ReactPy features.

    State is just one of those features, but you will meet the other Hooks later.

    Call Hooks only at the top level

    Hooks — functions starting with use — can only be called at the top level of your components or your own Hooks. You can't call Hooks inside conditions, loops, or other nested functions. Hooks are functions, but it's helpful to think of them as unconditional declarations about your component's needs. You "use" ReactPy features at the top of your component similar to how you "import" modules at the top of your file.

    The check is not just advice: the reactpy-flake8 plugin (the ReactPy analogue of eslint-plugin-react-hooks, and part of this repo's own lint config) reports REACTPY102 for a Hook under a branch or in a loop:

    @component
def bad(flag):
    a, _ = use_state("A")
    if flag:                      # REACTPY102 hook 'use_state' used inside if statement
        b, _ = use_state("B")
        return html.p(b)
    return html.p(a)

    Anatomy of use_state¶

    When you call use_state, you are telling ReactPy that you want this component to remember something:

    index, set_index = use_state(0)

    In this case, you want ReactPy to remember index.

    The convention is to name this pair like something, set_something. You could name it anything you like, but conventions make things easier to understand across projects.

    The only argument to use_state is the initial value of your state variable. In this example, the index's initial value is set to 0 with use_state(0).

    Every time your component renders, use_state gives you a pair containing two values:

    1. The state variable (index) with the value you stored.
    2. The state setter function (set_index) which can update the state variable and trigger ReactPy to render the component again.

    Here's how that happens in action:

    index, set_index = use_state(0)
    1. Your component renders the first time. Because you passed 0 to use_state as the initial value for index, it returns (0, set_index). ReactPy remembers 0 is the latest state value.
    2. You update the state. When a user clicks the button, it calls set_index(index + 1). index is 0, so it's set_index(1). This tells ReactPy to remember index is 1 now and triggers another render.
    3. Your component's second render. ReactPy still sees use_state(0), but because ReactPy remembers that you set index to 1, it returns (1, set_index) instead.
    4. And so on!

    Pass a function for an expensive initial value

    use_state accepts a callable and calls it only when the state is first created: use_state(lambda: json.loads(big_blob)). Passing the result of an expensive call instead — use_state(json.loads(big_blob)) — reparses on every render, because Python evaluates the argument before use_state ever runs.

    @component
def gallery():
    index, set_index = use_state(0)
    show_more, set_show_more = use_state(False)

    def handle_next(event):
        set_index(index + 1)

    def handle_more(event):
        set_show_more(not show_more)

    sculpture = sculptures[index]
    return html.div(
        html.button({"onClick": handle_next}, "Next"),
        html.h2(html.i(sculpture["name"]), " by ", sculpture["artist"]),
        html.h3(f"({index + 1} of {len(sculptures)})"),
        html.button(
            {"onClick": handle_more}, "Hide details" if show_more else "Show details"
        ),
        html.p(sculpture["description"]) if show_more else None,
        html.img({"src": sculpture["url"], "alt": sculpture["alt"]}),
    )

    Click "Next" in one gallery and the other doesn't budge. Each call to gallery() is a separate component instance with its own state.

    This is the same mechanism behind Passing Props to a Component: the person prop is local to one invocation of Profile(), so two Profile() calls don't share it. State works the same way.

    Because state belongs to the instance and not the function, two galleries can drift apart — which is sometimes what you want, and sometimes not. Sharing State Between Components covers the case where they must move together.

    How does ReactPy know which state to return?

    You might have noticed that the use_state call does not receive any information about which state variable it refers to. There is no "identifier" passed to use_state, so how does it know which state to return? Does it rely on some magic like parsing your functions? The answer is no.

    Instead, to enable their concise syntax, Hooks rely on a stable call order on every render of the same component. ReactPy appends each Hook's state to a list on the component's first render, then walks that list by position on every render after (LifeCycleHook.use_state in core/_life_cycle_hook.py). This works well in practice because if you follow the rule above ("only call Hooks at the top level"), Hooks are always called in the same order — and reactpy-flake8 catches most mistakes.

    What happens when the order does change is worth knowing, because one of the two outcomes fails silently:

    • A Hook appears where there was none before → IndexError: list index out of range, the render aborts, and the error is logged.
    • A Hook stops being called → the Hooks after it shift up one slot and quietly receive the wrong values. Nothing is logged, and the component keeps rendering.

    Measured with two use_state calls that vanish behind a branch, the surviving Hook got the first slot's value while its own was left orphaned. That is far harder to debug than a crash, which is exactly why the top-level rule is enforced rather than merely recommended.

    Recap¶

    • Components need to "remember" things, and that memory is called state.
    • A state variable is declared with use_state, which returns the current value and a setter function.
    • Updating a local variable doesn't re-render, and re-renders throw local variables away. State is what survives.
    • Hooks must be called at the top level, in the same order every render; reactpy-flake8 raises REACTPY102 otherwise.
    • State is local to each invocation of a component, so two instances never share it.

    Updating Objects in State

    Overview¶

    State can hold any kind of value, including dicts and lists. But you shouldn't change objects that you hold in ReactPy state directly. Instead, when you want to update an object, you need to create a new one (or make a copy of an existing one), and then set the state to use that copy.

    You will learn

    • How to correctly update an object in ReactPy state
    • How to update a nested object without mutating it
    • What immutability is, and how not to break it
    • Why a mutating update can be dropped without any error

    What's a mutation?¶

    To mutate something means to change it after it was created.

    Objects and lists in Python are mutable: you can change their contents in place. The mutating operations are usually visible in the code you write — obj["key"] = value, list.append(x), list.pop(), del list[i], d.update(other) — but there are more hiding behind method names that don't announce themselves (list.sort(), list.extend(), list.reverse(), dict.setdefault()).

    In ReactPy, treat state as read-only. Every time your code renders, you work with the state that already exists, and you want to cause changes over time based on user input. Leaving all mutation to the setter keeps your code easy to understand. This applies to state in general, not just object state.

    Mutating state doesn't just risk a bug — it can silently do nothing

    In React, mutating state is a "may render stale UI" hazard. In ReactPy it is sharper, because the setter compares the new value against the old one before scheduling anything — and that comparison accepts equality, not just identity (core/hooks.py, strictly_equal). Anything that compares equal, including a brand-new object, schedules no render.

    Measured behaviour, each case dispatched through reactpy.core.layout.Layout:

    What the handler does Result
    Mutates a list in place, then set_x(same_list) no render at all
    Mutates in place, calls no setter no render
    set_x([*old, item]) — a new object renders

    The failure is completely silent: no error, no warning, nothing in the browser console. Your handler ran, ReactPy agreed that nothing changed, and the UI never updates. This is why the read-only rule is not a style preference here.

    Treat state as read-only¶

    Consider a form that lets the user change their profile. This handler reaches into the state object and assigns a field directly:

    async def handle_first_name(event):
    person["firstName"] = await event.target.value   # 🚩 Mutate!
    set_person(person)                                # same object -> ignored

    person is the very object ReactPy already holds, so the assignment changes it in place and then hands the same object back. ReactPy compares it against what it already has, finds nothing changed, and skips the render — the field appears frozen while your dict quietly holds the new value.

    The fix is to always create a new object for the next state:

    async def handle_first_name(event):
    set_person({**person, "firstName": await event.target.value})

    That is the pattern for every state update in ReactPy: build a new value, pass it to the setter.

    There is no automatic merge

    set_x(...) replaces the state. It does not merge a partial object into what was there. Verified: setting {"a": 9} over {"a": 1, "b": 2} leaves {'a': 9} — "b" is simply gone.

    If you have read React tutorials, you may remember setState merging objects. That was the class API. React's own useState replaces, and so does ReactPy (core/hooks.py, _CurrentState.dispatch assigns self.value = new). Any ReactJS text saying "React merges the object into your current state" is describing an API that no longer applies — port those examples with an explicit {**old, ...}.

    Local mutation is fine

    Mutating a value you just created inside the current render is safe, because nothing else has ever seen it. The same applies to the rows = [] plus rows.append(...) loop you will write constantly when building children:

    @component
def list_of_parts(parts):
    # Built during this render, never handed out before.
    sorted_parts = sorted(parts, key=lambda p: p["importance"])
    return html.ul(
        [html.li({"key": p["id"]}, p["title"]) for p in sorted_parts]
    )

    What must not be mutated is state ReactPy gave you, and props you received. See Local mutation: Your component's little secret for the rendering-side version of this rule.

    Copying objects with the spread syntax¶

    To update an object, create a new one from the old one so you can change any of its properties. Python has no ... spread operator, but {**obj, "key": value} is the same operation on dicts, and [*items, x] is its twin for lists.

    @component
def form():
    person, set_person = use_state(
        {
            "firstName": "Jane",
            "lastName": "Jacobs",
            "email": "jane@example.com",
        }
    )

    async def handle_first_name(event):
        # Copy everything, then override just this one field.
        set_person({**person, "firstName": await event.target.value})

    async def handle_last_name(event):
        set_person({**person, "lastName": await event.target.value})

    async def handle_email(event):
        set_person({**person, "email": await event.target.value})

    return html.div(
        html.input({"value": person["firstName"], "onChange": handle_first_name}),
        html.input({"value": person["lastName"], "onChange": handle_last_name}),
        html.input({"value": person["email"], "onChange": handle_email}),
        html.hr(),
        html.h1(f"Hello, {person['firstName']} {person['lastName']}!"),
        html.a({"href": f"mailto:{person['email']}"}, person["email"]),

    An unpacked dict is a shallow copy

    {**person} copies the top level only. Any nested dict or list inside it is still shared with the previous state — see Updating a nested object.

    The destructuring equivalents

    Where React's docs reach for const { a, ...rest } = obj, Python reads with indexing and writes with unpacking. For the "everything but one key" shape, the direct translation is a comprehension:

    rest = {k: v for k, v in obj.items() if k != "drop"}

    @component
def form():
    person, set_person = use_state(
        {"firstName": "Jane", "lastName": "Jacobs", "email": "jane@example.com"}
    )

    # One handler for every field. ReactPy always calls a handler with the
    # event as its single positional argument, so the field name is bound by
    # the thin handlers below rather than delivered by the client.
    async def handle_change(field, event):
        set_person({**person, field: await event.target.value})

    async def handle_first_name_change(event):
        await handle_change("firstName", event)

    async def handle_last_name_change(event):
        await handle_change("lastName", event)

    async def handle_email_change(event):
        await handle_change("email", event)

    return html.div(
        html.input(
            {
                "value": person["firstName"],
                "onChange": handle_first_name_change,
            }
        ),
        html.input(
            {
                "value": person["lastName"],
                "onChange": handle_last_name_change,
            }
        ),
        html.input(
            {
                "value": person["email"],
                "onChange": handle_email_change,
            }
        ),
        html.hr(),
        html.h1(f"Hello, {person['firstName']} {person['lastName']}!"),
    )

    Note how the field name is bound by the thin per-field handler, not delivered by the client. ReactPy invokes every event handler with the event as its single positional argument — verified, a handler declaring two required parameters fails with TypeError: ... missing 1 required positional argument: 'event'. There is no e.target.name shortcut either: name is readable, but reading it costs a round trip to the page, and it has to be read from the element which fired the event. Any extra context which is already known on the server is cheaper bound in Python — by a named handler, a closure, or a functools.partial.

    Reach for use_reducer when handlers multiply

    Several handlers that all edit one object is a sign the update logic wants its own home. See Extracting State Logic into a Reducer.

    @component
def form():
    person, set_person = use_state(
        {
            "firstName": "Jane",
            "lastName": "Jacobs",
            "email": "jane@example.com",
            "shippingAddress": {
                "street": "123 Maple Street",
                "city": "Pretendville",
            },
        }
    )

    async def handle_city(event):
        address = {**person["shippingAddress"], "city": await event.target.value}
        set_person({**person, "shippingAddress": address})

    return html.div(
        html.label(
            "City: ",
            html.input(
                {
                    "value": person["shippingAddress"]["city"],
                    "onChange": handle_city,
                }
            ),
        ),
        html.h1(person["firstName"]),
        html.p(person["shippingAddress"]["street"]),
        html.p(person["shippingAddress"]["city"]),

    Two copies are required:

    1. Copy person["shippingAddress"] with the new "city".
    2. Copy person, replacing "shippingAddress" with that new dict.

    Writing person["shippingAddress"]["city"] = ... would mutate the nested dict in place. Because that nested dict is the same object the previous state still refers to, the change is invisible to ReactPy's comparison and the update is dropped.

    Objects are not really nested

    Python makes this point sharper than JavaScript does. Given:

    person = {"name": "Jane", "theme": {"background": "white"}}
copy = {**person}

    copy["theme"] and person["theme"] are the same dict. Python never deep-copies on assignment or on unpacking — copying is shallow for dicts, lists, and everything else. To get a genuinely independent copy you either copy each level explicitly, as the example does, or use copy.deepcopy:

    import copy

set_people(copy.deepcopy(people))

    deepcopy is the blunt instrument: correct, but slower, and it copies everything reachable, including objects you did not mean to duplicate. Prefer explicit copies for the paths you actually change, and keep state to plain dicts, lists, and primitives so deepcopy remains a safe fallback.

    Shallow sharing is also why two components seeded from the same module-level fixture end up aliasing each other's data — see Updating Arrays in State for the list version of that bug.

    Writing concise update logic¶

    React's docs reach for Immer here, which records your mutations through a proxy and turns them into copies. ReactPy has no Immer and no equivalent. There is no proxy layer, so nothing could observe your mutations, and there is no use_immer to import.

    What you have instead:

    • Dict and list unpacking — {**obj, "k": v}, [*items, x]. This covers the overwhelming majority of updates and is what every example above uses.
    • copy.deepcopy — for the rare shape too deep to copy by hand.
    • use_reducer — does not shorten updates, but moves them out of the component so their verbosity costs you less. See Extracting State Logic into a Reducer.

    Resist building your own Immer. A proxy that logs mutations would have to run on the server, after a websocket round trip, which is not the problem Immer solves in the browser. If update logic feels genuinely painful, that usually means the state shape is wrong — see Choosing the State Structure.

    Recap¶

    • Treat everything ReactPy hands you as state or props as read-only: never assign into it, never call a mutating method on it.
    • Build a new object with {**old, ...} and pass that to the setter.
    • Mutating in place and passing the same object back is silently dropped — ReactPy compares the new value with the old and schedules no render when they are equal. Nothing in the browser will tell you.
    • Copying is shallow at every level; copy all the way up from the field that changed, or use copy.deepcopy.
    • Mutating a value you created during this render is fine.
    • There is no Immer in ReactPy; use dict and list unpacking, or restructure the state.
